# 실시간 위치 공유 + 동적 지오펜싱 — 데이터가 한 바퀴 도는 흐름

> 이 문서는 "프론트에서 위치를 받아서 → 서버로 보내고 → 상대방 위치를 받아와서 → 지도에 그리고 → 접근/이탈을 판정"하는 전체 흐름을 실제 코드 기준으로 풀어서 설명한다.
> **개념·흐름은 이 문서**, **파일별 실제 코드는 [11_지오펜싱_테스트_구현코드.md](11_지오펜싱_테스트_구현코드.md)** 를 본다.
> (2026-08-19 현행화 — 이 기능은 커밋 `0dcfcf8`, `3af1c90` 으로 main에 들어가 있다.)

## 0. 먼저, 질문 하나 정정하고 시작

원래 질문: *"프론트에서 위치를 받아서 백엔드에 넘겨서 **계산하고** 다시 뷰로 보이게 하는 거지?"*

**절반만 맞다.** 우리 구조에서 백엔드는 **계산을 하지 않는다.** 백엔드가 하는 일은 딱 두 가지 — **보관**과 **중계**다.

| 역할 | 어디서 하나 | 실제 코드 |
|------|-----------|----------|
| 위치 **획득** (GPS) | 프론트 | `navigator.geolocation.watchPosition` |
| 위치 **보관** | 백엔드 | `ConcurrentHashMap` (메모리) |
| 위치 **중계** (남들 것 나눠주기) | 백엔드 | `GET /api/locations` |
| 거리 **계산** (지오펜스 판정) | **프론트** | `map.distance(...)` ← 여기가 포인트 |
| 마커 **렌더링** | 프론트 | `L.marker`, `setLatLng` |

왜 계산을 프론트에서 하나? 지금 판정은 "**나**의 반경 220m 안에 상대가 있나"라서, 내 화면에서 나 기준으로만 계산하면 충분하기 때문이다. 서버는 모든 유저의 판정을 다 해줄 필요 없이 위치 목록만 던져주면 되고, 각자의 브라우저가 자기 기준으로 판정한다.

> 백엔드 계산이 필요해지는 경우도 있다: 판정 결과를 DB에 기록해야 하거나(라이딩 로그), 클라이언트를 신뢰하면 안 되는 상황(게임 치팅 방지), 수백 명 규모의 매칭. 그때는 같은 거리 계산을 서버(PostGIS `ST_DWithin` 등)로 옮기면 된다.

## 1. 전체 그림 — 데이터 한 바퀴

```
[내 브라우저]                         [백엔드]                        [상대 브라우저]
                                (Spring Boot, 메모리)
 ① GPS 획득
 watchPosition ──┐
                 │  (위치공유 체크가 켜져 있을 때만)
                 │  ② 3초마다 보고
                 └─ POST /api/locations ──▶ ConcurrentHashMap
                                            userId → {name, lat, lng, 시각}
                                                 ▲
                                                 │ (상대도 똑같이 ①②를 한다)
                 ┌─ GET /api/locations?userId=나 ┘
                 │  ③ 3초마다 조회 (나를 뺀 목록이 옴)
 ④ 지도에 반영 ◀─┘
   - 주황 마커 생성/이동
 ⑤ 지오펜스 판정
   - 거리 계산 → 밖↔안 전이 감지 → 이벤트
```

핵심 리듬: **"보고(POST)와 조회(GET)를 3초마다 반복"** — 이걸 폴링(polling)이라 한다. 서버가 먼저 연락하는 방법(WebSocket)도 있지만, 폴링은 기존 REST 패턴만으로 만들 수 있어서 먼저 채택했다.

## 2. ① GPS 획득 — 프론트 (MapPage.js)

브라우저 내장 API가 위치가 바뀔 때마다 콜백을 불러준다.

```js
navigator.geolocation.watchPosition((pos) => {
  const { latitude, longitude } = pos.coords;
  lastPosRef.current = { lat: latitude, lng: longitude };  // ★ 최신 위치를 ref에 보관
  // ... 내 파란 마커 + 220m 원도 여기서 이동
}, onError, { enableHighAccuracy: true, maximumAge: 5000, timeout: 10000 });
```

포인트: 위치를 받자마자 서버로 쏘지 않고 `lastPosRef`에 **담아두기만** 한다. 전송은 3초 타이머가 따로 한다. 이렇게 분리하면 GPS가 1초에 몇 번씩 갱신돼도 서버 요청은 3초에 1번으로 유지된다 (전송량 제어).

옵션 3개의 뜻:

| 옵션 | 뜻 |
|------|-----|
| `enableHighAccuracy: true` | GPS 칩을 써서 정밀하게 (배터리를 더 씀) |
| `maximumAge: 5000` | 5초 이내 캐시된 위치는 재사용해도 됨 |
| `timeout: 10000` | 10초 안에 못 얻으면 에러 콜백 |

> 이 effect는 **위치공유 체크와 무관하게 항상 실행된다.** 내 위치 마커는 공유 여부와 상관없이
> 지도에 보여야 하기 때문. 공유 여부가 관여하는 건 "서버로 보내느냐"뿐이다.

## 3. ② 보고 — 프론트 → 백엔드

3초마다 도는 타이머(`setInterval`) 안에서:

```js
const myPos = lastPosRef.current;
if (!myPos || !locationShareEnabled) return;   // ★ 위치가 없거나 공유 OFF면 아무것도 안 함

await reportLocation({ userId: myId, name: myName, lat: myPos.lat, lng: myPos.lng });
// 내부적으로: POST /api/locations  body = { userId, name, lat, lng }
```

- `myId`: 로그인했으면 진짜 userId, 아니면 탭마다 만든 임시 ID (sessionStorage)
- `myName`: 로그인 이름, 없으면 `게스트1234`
- API 호출은 `api/locations.js` → 공통 클라이언트 `api/client.js`를 거친다 (fetch 직접 호출 금지 규칙)

**위치 공유는 사용자가 켜야 동작한다 (opt-in).** MapPage 왼쪽 패널의 "위치 공유" 체크박스가
`locationShareEnabled` state를 바꾸고, 그 값이:

1. `localStorage` 에 저장되고 (새로고침해도 유지)
2. 로그인 상태면 `PUT /api/auth/users/{id}/location-sharing` 으로 DB에도 저장되고
3. 이 폴링 effect의 의존성이라, 끄는 순간 effect가 정리(cleanup)되면서 **상대방 마커도 전부 사라진다**

```js
}, [user?.id, locationShareEnabled]);   // 이 둘 중 하나가 바뀌면 타이머를 새로 건다
```

오프라인일 때 서버 저장은 실패하지만 localStorage에는 남고, 나중에 `online` 이벤트가 뜨면
다시 서버에 동기화한다.

```js
window.addEventListener('online', handleOnline);   // 온라인 복귀 시 DB와 재동기화
```

## 4. 보관 — 백엔드 (LocationController.java)

```java
private final Map<Long, LiveLocation> locations = new ConcurrentHashMap<>();

@PostMapping("/locations")
public ResponseEntity<?> report(@RequestBody LocationReport req) {
    if (req.userId() == null || req.lat() == null || req.lng() == null) {
        return ResponseEntity.badRequest().body(Map.of("message", "userId, lat, lng는 필수입니다"));
    }
    String name = (req.name() == null || req.name().isBlank()) ? "익명" : req.name();
    locations.put(req.userId(),
        new LiveLocation(req.userId(), name, req.lat(), req.lng(), System.currentTimeMillis()));
    return ResponseEntity.ok(Map.of("message", "ok"));
}
```

**왜 DB가 아니라 메모리인가?** 실시간 위치는 3초 뒤면 낡는 데이터다. 영구 보관 가치가 없고, 조회/갱신이 초 단위로 빈번하다 → DB에 쓰면 느리고 낭비. `ConcurrentHashMap`은 여러 요청이 동시에 읽고 써도 안전한 맵이다.

같은 이유로 **유통기한**도 있다. 마지막 보고 후 15초가 지나면 접속 종료로 간주하고 지운다:

```java
locations.values().removeIf(l -> now - l.updatedAt() > STALE_MS);  // STALE_MS = 15_000
```

**메모리 방식의 한계** (알고는 있어야 한다)

- 서버를 재시작하면 전부 사라진다 (실시간 데이터라 문제없음)
- 서버를 2대 이상으로 늘리면 **각 서버가 서로 다른 맵을 갖게 되어** 위치가 안 보인다
  → 그때는 Redis 같은 공유 저장소나 WebSocket 브로커로 옮겨야 한다

## 5. ③ 조회 — 백엔드 → 프론트

```java
@GetMapping("/locations")
public ResponseEntity<List<LiveLocation>> others(@RequestParam Long userId) {
    long now = System.currentTimeMillis();
    locations.values().removeIf(l -> now - l.updatedAt() > STALE_MS);   // 유통기한 정리
    return ResponseEntity.ok(locations.values().stream()
            .filter(l -> !l.userId().equals(userId))                     // "나"는 빼고
            .toList());
}
```

응답 예시 (JSON):

```json
[ { "userId": 902, "name": "테스트B", "lat": 37.5670, "lng": 126.9785, "updatedAt": 1784885912594 } ]
```

## 6. ④ 렌더링 — 받은 목록을 지도에 반영

받은 목록을 돌면서 "**없으면 만들고, 있으면 옮긴다**" — 내 위치 마커와 같은 패턴이다.

```js
let marker = markers.get(o.userId);
if (!marker) {
  marker = L.marker([o.lat, o.lng], { icon: makeOtherUserIcon(), zIndexOffset: 900 })  // 주황 점
    .bindTooltip(o.name, { permanent: true, direction: 'top', offset: [0, -10] })      // 이름표
    .addTo(map);
  markers.set(o.userId, marker);
} else {
  marker.setLatLng([o.lat, o.lng]);  // 매번 새로 만들지 않고 좌표만 이동
}
```

마커를 매번 지웠다 새로 만들면 화면이 깜빡이고 비용도 크다. 그래서 **마커 대장**을 하나 두고
"이미 있는 마커는 좌표만 갱신"한다. 대장은 `Map(userId → marker)` 구조의 `useRef` 다 —
렌더링과 무관한 객체 보관은 state가 아니라 ref를 쓴다.

응답에 더 이상 없는 유저(= 서버에서 15초 유통기한으로 지워진 유저)는 마커를 제거한다.

```js
for (const [id, marker] of markers) {
  if (!seen.has(id)) {                       // 이번 응답에 없던 유저
    if (insideMap.get(id)) setStatus(`📡 ${name}님 연결 끊김`);
    marker.remove(); markers.delete(id); insideMap.delete(id);
  }
}
```

## 7. ⑤ 지오펜스 판정 — 이벤트는 "전이"에서만 발생

```js
const dist = map.distance([myPos.lat, myPos.lng], [o.lat, o.lng]);  // 미터 단위
const wasInside = insideMap.get(o.userId) || false;
const isInside = wasInside ? dist <= GEOFENCE_EXIT_M      // 안에 있었으면 250m까지는 '안'
                           : dist <= GEOFENCE_RADIUS_M;   // 밖에 있었으면 220m부터 '안'

if (isInside && !wasInside) {          // 밖 → 안 : 진입 이벤트!
  setStatus(`⚠️ ${o.name}님이 220m 안에 접근! (거리 ${Math.round(dist)}m)`);
  marker.bindPopup(`${o.name} — ${Math.round(dist)}m 거리`).openPopup();
} else if (!isInside && wasInside) {   // 안 → 밖 : 이탈 이벤트!
  setStatus(`🚨 ${o.name}님이 범위를 벗어났습니다 (거리 ${Math.round(dist)}m)`);
}
insideMap.set(o.userId, isInside);     // 이번 상태를 기억 → 다음 판정의 "이전 상태"가 됨
```

**가장 중요한 개념: "안에 있다"가 아니라 "밖→안으로 바뀌는 순간"을 잡는다.**
그냥 `isInside`만 보면 3초마다 알림이 도배된다. 이전 상태(`wasInside`)와 비교해서 **상태가 바뀐 순간에만** 이벤트를 쏜다 — 이것이 지오펜싱의 핵심 패턴이다.

| 이벤트 | 조건 | 현재 |
|--------|------|------|
| 진입 (enter) | `isInside && !wasInside` | ✅ 구현됨 |
| 이탈 (exit) | `!isInside && wasInside` | ✅ 구현됨 |
| 연결 끊김 | 안에 있던 유저가 응답 목록에서 사라짐 | ✅ 구현됨 (이탈과 구분해서 알림) |
| 체류 (dwell) | inside 상태가 N초 이상 지속 | ❌ 미구현 |

### 히스테리시스 — 경계 떨림 막기

GPS 오차는 도심에서 수십 미터씩 난다. 문턱이 220m 하나뿐이면 219m ↔ 221m 를 오가며
"접근! 이탈! 접근! 이탈!" 이 3초마다 반복된다.

그래서 **들어올 때와 나갈 때의 문턱을 다르게** 뒀다.

```
          220m          250m
   ────────┼─────────────┼────────
   밖에 있을 때 → 220m 안으로 들어와야 '진입'
   안에 있을 때 → 250m 밖으로 나가야 '이탈'
            ↑ 이 30m 구간이 완충지대
```

```js
const GEOFENCE_RADIUS_M = 220;   // 진입 문턱
const GEOFENCE_EXIT_M   = 250;   // 이탈 문턱
```

이걸 **히스테리시스(hysteresis)** 라고 한다. 온도조절기(24도에 켜고 26도에 끄기)와 같은 원리.

> 실험해보기: `GEOFENCE_RADIUS_M` 을 300으로 바꾸고 두 탭을 띄워보면 판정이 어떻게 달라지는지 바로 보인다.

## 8. 요약 — 한 문장씩

1. **프론트**가 GPS로 위치를 얻어 ref에 보관한다 (`watchPosition`)
2. 위치공유가 켜져 있으면 3초마다 **프론트 → 백엔드**로 내 위치를 보고한다 (`POST /api/locations`)
3. **백엔드**는 계산 없이 메모리에 보관만 하고, 15초 지난 것은 버린다
4. 3초마다 **백엔드 → 프론트**로 나를 뺀 접속자 목록을 받는다 (`GET /api/locations`)
5. **프론트**가 마커를 그리고, 거리 계산과 지오펜스 판정(상태 전이 감지)까지 수행한다
6. 진입/이탈은 **히스테리시스(220/250m)** 로, 접속 종료는 **15초 무보고**로 구분한다

> 관련 파일: `MapPage.js` (폴링 + 판정) · `api/locations.js` (API 호출) · `utils/leaflet.js` (아이콘) · `LocationController.java` (보관/중계)

## 9. 남은 개선 후보

| 항목 | 지금 | 개선 방향 |
|------|------|----------|
| 통신 방식 | 3초 폴링 | WebSocket(STOMP) — 서버가 먼저 밀어주기 |
| 저장소 | 서버 메모리 | Redis — 서버를 여러 대로 늘려도 공유됨 |
| 공유 범위 | **접속자 전원에게 공개** | 같은 파티(링크) 멤버끼리만 공유 |
| 인증 | userId를 그대로 믿음 | 토큰에서 userId 추출 (사칭 방지) |
| 체류 이벤트 | 없음 | "N분 이상 함께 있었음" 판정 |
