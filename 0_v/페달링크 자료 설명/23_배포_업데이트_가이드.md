# 배포 · 업데이트 가이드 — 고친 것을 서버에 올리기

> [22_서버_운영_가이드.md](22_서버_운영_가이드.md) 가 **서버를 돌리는 법**이라면,
> 이 문서는 **코드를 고친 뒤 서버에 반영하는 법**이다.
> 대상: Rocky VM `192.168.253.128` · 계정 `user1`

---

## 먼저 — 무엇을 고쳤는지 정한다

절차가 달라지므로 이것부터 판단한다.

```
프론트만 고쳤나?          → 1번 (가장 간단)
백엔드 로직만 고쳤나?      → 2번
엔티티에 필드를 넣었나?    → 3번 (DB 작업 추가)
Nginx 설정을 고쳤나?      → 4번
```

| 고친 것 | 빌드 | 전송 | 재시작 | DB |
|---|---|---|---|---|
| 프론트 (jsx·css) | `npm run build` | 정적 파일 | ❌ 불필요 | — |
| 백엔드 로직 | `gradlew bootJar` | JAR | ✅ `pedallink` | — |
| **엔티티 필드** | `gradlew bootJar` | JAR | ✅ | ⚠️ **스키마 반영** |
| Nginx 설정 | — | — | ✅ `nginx reload` | — |

---

## 0. 배포 전 — 커밋부터

문제가 생겼을 때 **어디로 되돌릴지** 알 수 있어야 한다.

```powershell
cd c:\Users\kimHosung\projects
git status                      # 뭘 바꿨는지 확인
git add -A
git commit -m "feat: 무엇을 했는지"
git push origin main
```

커밋하지 않고 배포하면, 나중에 "서버에 올라간 게 정확히 어느 코드인지" 알 수 없다.

---

## 1. 프론트만 고쳤을 때

### 윈도우

```powershell
cd c:\Users\kimHosung\projects\my-app-front
npm run build
```

**빌드 결과에 절대주소가 없는지 확인한다.**

```powershell
Select-String -Path build\assets\*.js -Pattern "localhost:8080|trycloudflare"
```

아무것도 안 나와야 정상이다. 나오면 `.env.production` 이 비어 있는지 확인할 것.

```powershell
scp -r build\* user1@192.168.253.128:~/front/
```

### VM

```bash
sudo cp -r ~/front/* /var/www/pedallink/
sudo restorecon -Rv /var/www/pedallink
```

**Nginx 재시작은 필요 없다.** 정적 파일이라 다음 요청부터 바로 새 파일이 나간다.

### 확인

브라우저에서 `Ctrl+Shift+R`(강력 새로고침) 후 개발자도구 → Network 에서
`index-XXXX.js` 의 **해시가 바뀌었는지** 본다.

> Vite 는 내용이 바뀌면 파일명 해시도 바꾼다(`index-BKHp1rps.js` → `index-A1b2C3d4.js`).
> 그래서 JS·CSS 는 캐시 문제가 거의 없다. 다만 `index.html` 은 이름이 고정이라
> 간혹 캐시될 수 있으므로 강력 새로고침으로 확인한다.

## 2. 백엔드를 고쳤을 때

### 윈도우

```powershell
cd c:\Users\kimHosung\projects\my-app-backend
$env:JAVA_HOME = "C:\Program Files\Java\jdk-21.0.10"
.\gradlew bootJar
```

**다른 이름으로 전송한다.**

```powershell
scp build\libs\my-app-backend-0.0.1-SNAPSHOT.jar user1@192.168.253.128:~/pedallink-new.jar
```

### VM — 멈추고 · 바꾸고 · 시작

```bash
sudo systemctl stop pedallink
mv ~/pedallink-new.jar ~/pedallink.jar
sudo systemctl start pedallink
sudo systemctl status pedallink --no-pager
```

`Active: active (running)` 이면 성공이다.

### ⚠️ 왜 다른 이름으로 받는가

리눅스는 **실행 중인 파일도 덮어쓸 수 있다.** 윈도우처럼 "사용 중이라 못 바꿈" 이 아니다.

그런데 Spring Boot 는 클래스를 **필요할 때마다 JAR 에서 꺼내 쓴다.** 돌아가는 중에 파일이 바뀌면
아직 안 읽은 클래스를 찾지 못해 이런 오류가 난다.

```
java.lang.NoClassDefFoundError
java.lang.ClassNotFoundException
```

증상이 엉뚱하게 나타나서 원인 찾기가 어렵다. **멈춘 뒤에 바꾸는 것**이 안전하다.

## 3. 엔티티에 필드를 넣었을 때 ⚠️

2번을 먼저 한 뒤, **스키마 반영 단계를 추가**한다.

### 3-1. 어떤 타입을 추가했는지 확인

| 추가한 타입 | `ddl-auto=update` | 이유 |
|---|---|---|
| `String` `Integer` `Long` `Double` | ✅ 자동 생성 | nullable 이라 기존 행에 NULL 이 들어감 |
| `boolean` `int` `long` (원시타입) | ❌ **실패** | NOT NULL 인데 기존 행을 채울 값이 없음 |

### 3-2. 객체 타입이면 — update 한 번

```bash
# validate → update
sudo sed -i 's/ddl-auto=validate/ddl-auto=update/' /etc/systemd/system/pedallink.service
sudo systemctl daemon-reload
sudo systemctl restart pedallink

# 컬럼이 생겼는지 확인
sudo -u postgres psql -d Pedal_link -c "\d 테이블명"

# DDL 오류가 없었는지 확인 (중요)
sudo journalctl -u pedallink -n 100 --no-pager | grep -i "error executing ddl" || echo "DDL 오류 없음"

# update → validate 되돌리기
sudo sed -i 's/ddl-auto=update/ddl-auto=validate/' /etc/systemd/system/pedallink.service
sudo systemctl daemon-reload
sudo systemctl restart pedallink
```

### 3-3. 원시타입이면 — SQL 직접

`ddl-auto` 로는 안 되므로 마이그레이션 파일을 만든다.

```bash
sudo -u postgres psql -d Pedal_link
```

```sql
ALTER TABLE 테이블명
    ADD COLUMN IF NOT EXISTS 컬럼명 BOOLEAN NOT NULL DEFAULT FALSE;
```

**`DEFAULT` 가 핵심이다.** 이게 없으면 기존 행을 채울 수 없어 PostgreSQL 이 거부한다.

프로젝트의 `DB/migrations/` 에도 같은 파일을 남겨 팀원과 공유한다.

### 3-4. ⚠️ `validate` 로 되돌리는 것을 잊지 말 것

`update` 로 두면 **컬럼 생성에 실패해도 WARN 만 남기고 정상 기동한다.**
`Started MyAppBackendApplication` 만 보면 멀쩡해 보여서 발견이 늦어진다.

`validate` 는 코드와 DB 가 어긋나면 **기동을 실패시켜 즉시 알려준다.**
발표 당일에 조용히 깨져 있는 것보다 훨씬 낫다.

## 4. Nginx 설정을 고쳤을 때

```bash
sudo vi /etc/nginx/conf.d/pedallink.conf
sudo nginx -t                    # 문법 검사 — 반드시 먼저
sudo systemctl reload nginx
```

| 명령 | 차이 |
|---|---|
| `reload` | 설정만 다시 읽음 · **접속이 끊기지 않음** |
| `restart` | 완전 재시작 · 순간 끊김 |

평소에는 `reload` 로 충분하다.

> `nginx -t` 를 건너뛰고 `reload` 하면, 문법 오류가 있어도 **이전 설정으로 계속 돌아가서**
> "고쳤는데 왜 안 바뀌지?" 상황이 된다. 항상 `-t` 먼저.

## 5. 반영됐는지 확인

```bash
# 파일 시각
ls -l ~/pedallink.jar /var/www/pedallink/index.html

# 백엔드 재시작 시각
sudo systemctl status pedallink --no-pager | grep Active

# 응답
curl -I http://localhost/
curl http://localhost/api/crews
```

`Active: active (running) since ...` 의 시각이 **방금 배포한 시각**이어야 한다.

## 6. 롤백 — 되돌리기

### 백엔드

배포 전 JAR 을 남겨두면 쉽다. 위 2번 절차를 쓰면 `~/pedallink.jar` 이 항상 직전 버전이므로,
백업을 하나 더 두는 습관을 들인다.

```bash
# 배포 전에
cp ~/pedallink.jar ~/pedallink-prev.jar

# 되돌릴 때
sudo systemctl stop pedallink
cp ~/pedallink-prev.jar ~/pedallink.jar
sudo systemctl start pedallink
```

### 프론트

```bash
# 배포 전에
sudo cp -r /var/www/pedallink /var/www/pedallink-prev

# 되돌릴 때
sudo rm -rf /var/www/pedallink
sudo mv /var/www/pedallink-prev /var/www/pedallink
sudo restorecon -Rv /var/www/pedallink
```

### DB

**스키마 변경은 자동 롤백이 안 된다.** 컬럼을 추가했으면 직접 지워야 한다.

```sql
ALTER TABLE 테이블명 DROP COLUMN IF EXISTS 컬럼명;
```

그래서 스키마를 바꾸기 전에 **덤프를 떠두는 것**이 안전하다.

```bash
sudo -u postgres pg_dump -d Pedal_link -F p --no-owner --no-privileges \
  > ~/backup-$(date +%Y%m%d-%H%M).sql
```

## 7. 전체 재배포 — 프론트 + 백엔드 한 번에

발표 직전처럼 전부 최신으로 맞출 때 쓴다.

```powershell
# [윈도우] 빌드 2개
cd c:\Users\kimHosung\projects\my-app-front
npm run build

cd ..\my-app-backend
$env:JAVA_HOME = "C:\Program Files\Java\jdk-21.0.10"
.\gradlew bootJar

# 전송
cd ..
scp -r my-app-front\build\* user1@192.168.253.128:~/front/
scp my-app-backend\build\libs\my-app-backend-0.0.1-SNAPSHOT.jar user1@192.168.253.128:~/pedallink-new.jar
```

```bash
# [VM]
cp ~/pedallink.jar ~/pedallink-prev.jar        # 백업

sudo systemctl stop pedallink
mv ~/pedallink-new.jar ~/pedallink.jar
sudo cp -r ~/front/* /var/www/pedallink/
sudo restorecon -Rv /var/www/pedallink
sudo systemctl start pedallink

sleep 15
sudo systemctl status pedallink --no-pager | grep Active
curl -I http://localhost/
curl http://localhost/api/crews
```

## 8. 자주 하는 실수

| 실수 | 증상 | 예방 |
|---|---|---|
| 돌아가는 중에 JAR 덮어쓰기 | `NoClassDefFoundError` | 다른 이름으로 받고 stop 후 교체 |
| `restorecon` 누락 | **403 Forbidden** | 프론트 복사 후 항상 실행 |
| `ddl-auto` 를 `update` 로 방치 | 스키마 불일치를 조용히 넘김 | 작업 후 `validate` 복귀 |
| `nginx -t` 생략 | 고쳤는데 안 바뀜 | `reload` 전에 항상 검사 |
| `scp` 콜론 생략 | 로컬 복사됨 | 비밀번호를 묻는지로 판별 |
| `.env.production` 확인 안 함 | 빌드에 옛 주소가 박힘 | 빌드 후 `Select-String` 으로 검사 |
| 커밋 없이 배포 | 되돌릴 지점을 모름 | 배포 전 커밋·푸시 |

## 9. 요약 — 상황별 명령

### 프론트만

```
[윈] npm run build → scp -r build\* user1@VM:~/front/
[VM] sudo cp -r ~/front/* /var/www/pedallink/ && sudo restorecon -Rv /var/www/pedallink
```

### 백엔드만

```
[윈] .\gradlew bootJar → scp ...jar user1@VM:~/pedallink-new.jar
[VM] sudo systemctl stop pedallink && mv ~/pedallink-new.jar ~/pedallink.jar && sudo systemctl start pedallink
```

### 스키마 변경 포함

```
위 백엔드 절차 + ddl-auto update 한 번 → 컬럼 확인 → validate 복귀
```

### Nginx 설정

```
sudo nginx -t && sudo systemctl reload nginx
```
