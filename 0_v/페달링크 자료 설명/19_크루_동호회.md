# 크루(동호회) — 정기 라이딩 모임

## 이 프로젝트에서 쓰인 곳
- `/crew` 화면 — 크루 찾기 / 내 크루 탭
- 크루 생성, 가입 신청·승인·거절
- 크루 전용 채팅
- 정기 라이딩 일정 표시

관련 코드
- 백엔드 `controller/CrewController.java`, `service/CrewService.java`, `entity/Crew.java` 외 3개
- 프론트 `pages/CrewPage.jsx`, `api/crews.js`

## 파티와 무엇이 다른가

두 기능 모두 "사람을 모은다" 는 점은 같지만 **수명과 목적**이 다르다.

| | 파티 | 크루 |
|---|---|---|
| 기준 | **특정 코스 1개** | 지역·요일 |
| 수명 | 한 번 타고 끝 | 계속 유지 |
| 인원 | 소수 (기본 6명) | 제한 없음 |
| 끝나면 | 해산 | 그대로 남음 |
| 채팅 | `chat_messages` | `crew_chat_messages` |

코드 구조는 파티를 그대로 본떴다. `party_members` ↔ `crew_members` 가 거의 1:1 로 대응한다.

## 테이블 4개

```
crews              크루 본체 (이름·지역·일정·가입정책)
crew_members       멤버 (role: leader|member, status: pending|joined)
crew_events        정기 라이딩 일정
crew_chat_messages 크루 채팅 내역
```

### Crew

`entity/Crew.java`

```java
@ManyToOne @JoinColumn(name = "leader_user_id", nullable = false)
private User leader;

@Column(nullable = false, length = 100)
private String name;

private String region;         // "서울 · 반포"
private String scheduleText;   // "매주 토 07:00"
private String tag;            // "초보 환영"
private String description;

@Column(nullable = false, length = 20)
private String joinPolicy = "approval";   // open | approval

private String coverPhoto;
```

**`scheduleText` 가 문자열인 이유** — "매주 토 07:00", "격주 일 08:00" 처럼 표현이 자유롭다.
구조화하면 화면에 다시 문장으로 바꿔야 해서, 지금 규모에서는 문자열이 단순하다.
일정 알림 같은 기능이 붙으면 그때 요일·시각 컬럼으로 분리하면 된다.

### CrewMember

```java
private String role;     // leader | member
private String status;   // pending | joined
private String attend;   // yes | no | unknown  (이번 주 참석 여부)
```

`role` 과 `status` 를 나눈 이유는 **권한과 가입 상태가 별개**이기 때문이다.
리더도 `status` 는 `joined` 이고, 승인 대기 중인 사람은 `member` + `pending` 이다.

## 가입 정책 — open / approval

`service/CrewService.java`

```java
public CrewResponse join(Long crewId, Long userId) {
    if (crewMemberRepository.existsByCrewAndUser(crew, user)) {
        throw new RuntimeException("이미 신청했거나 가입한 크루입니다.");
    }

    CrewMember member = new CrewMember();
    member.setCrew(crew);
    member.setUser(user);
    member.setRole("member");
    member.setStatus("open".equals(crew.getJoinPolicy()) ? "joined" : "pending");
    crewMemberRepository.save(member);
    ...
}
```

| `joinPolicy` | 신청하면 | 리더 승인 |
|---|---|---|
| `open` | 바로 `joined` | 불필요 |
| `approval` | `pending` | 필요 |

**중복 검사가 `existsByCrewAndUser` 하나로 끝나는 이유** — `pending` 이든 `joined` 든
이미 행이 있으면 신청을 막아야 하므로 status 를 볼 필요가 없다.

## 크루 생성 — 리더 자동 가입

```java
@Transactional
public CrewResponse createCrew(CrewRequest req) {
    User leader = findUser(req.getLeaderId());

    Crew crew = new Crew();
    crew.setLeader(leader);
    ...
    Crew saved = crewRepository.save(crew);

    // 리더는 자동으로 joined 상태로 참여
    CrewMember leaderMember = new CrewMember();
    leaderMember.setCrew(saved);
    leaderMember.setUser(leader);
    leaderMember.setRole("leader");
    leaderMember.setStatus("joined");
    leaderMember.setAttend("yes");
    crewMemberRepository.save(leaderMember);
    saved.getMembers().add(leaderMember);
    ...
}
```

**리더를 `crew_members` 에도 넣는 이유.** `crews.leader_user_id` 만 있으면
멤버 목록을 만들 때마다 "리더 + 멤버들" 을 따로 합쳐야 한다.
멤버 테이블에 함께 넣어두면 **목록 조회가 한 번의 쿼리로 끝난다.**

`saved.getMembers().add(...)` 를 호출하는 것은 같은 트랜잭션 안에서 만든 응답에
방금 추가한 멤버가 빠지지 않게 하기 위해서다.

## myState 를 서버가 안 주는 이유

`dto/CrewResponse.java` 맨 위 주석에 근거가 적혀 있다.

```java
// myState(가입 상태)는 여기 안 담는다 — 보는 사람마다 다른 값이라 GET 목록/상세는
// 개인화 없이 그대로 두고, 프론트(CrewPage)가 로그인 유저 id로 직접 계산한다.
```

같은 크루라도 **A 에게는 `joined`, B 에게는 `none`** 이다.
서버가 개인화하면 사용자마다 응답이 달라져 캐시도 못 하고 API 도 복잡해진다.

프론트는 이미 받은 `members` / `pendingRequests` 배열로 계산한다.

`pages/CrewPage.jsx`

```js
const withMyState = (c) => {
  const isLeader  = c.leaderId === user?.id;
  const isMember  = (c.members || []).some((m) => m.userId === user?.id);
  const isPending = (c.pendingRequests || []).some((m) => m.userId === user?.id);
  return { ...c, myState: isLeader || isMember ? 'joined' : isPending ? 'pending' : 'none' };
};
```

파티 도크의 `myStateOf` 와 같은 패턴이다.

## 화면 구성 — 찾기 / 내 크루

```js
const myCrews   = crews.filter((c) => c.myState === 'joined');
const findCrews = crews.filter((c) => c.myState !== 'joined');
const shown     = view === 'mine' ? myCrews : findCrews;
```

**"크루 찾기" 에서 이미 가입한 크루를 뺀다.** 찾기 탭은 새로 들어갈 곳을 고르는 화면이므로
이미 속한 크루가 섞이면 목적이 흐려진다.

`pending`(승인 대기)은 찾기에 남겨둔다. 신청한 자리에서 상태를 확인할 수 있어야 하기 때문이다.
승인되면 그때 내 크루로 넘어간다.

빈 상태 문구도 경우를 나눈다.

```js
{crews.length === 0 ? t.noCrew : t.noCrewToFind}
```

크루가 하나도 없는 것과, 다 가입해서 찾을 게 없는 것은 **다른 상황**이다.

## API

| 메서드 | 경로 | 기능 |
|---|---|---|
| GET | `/api/crews` | 목록 |
| GET | `/api/crews/{id}` | 상세 |
| POST | `/api/crews` | 생성 |
| POST | `/api/crews/{id}/join` | 가입 신청 |
| POST | `/api/crews/{id}/leave` | 탈퇴 |
| POST | `/api/crews/{id}/requests/{userId}/approve` | 승인 |
| POST | `/api/crews/{id}/requests/{userId}/reject` | 거절 |

모든 응답이 **갱신된 크루 전체**(`CrewResponse`)다. 프론트는 받은 것으로 목록의 해당 항목만 교체하면 되고,
목록을 다시 불러올 필요가 없다.

```js
const replace = (updated) =>
  setCrews((prev) => prev.map((c) => (c.id === updated.id ? { ...c, ...updated } : c)));
```

## 예외 처리 방식

`CrewController` 는 `handle()` 로 예외를 한 곳에서 잡는다.

```java
private ResponseEntity<?> handle(Supplier<CrewResponse> action) {
    try {
        return ResponseEntity.ok(action.get());
    } catch (RuntimeException e) {
        return ResponseEntity.badRequest().body(Map.of("message", e.getMessage()));
    }
}
```

서비스에서 던진 메시지가 그대로 `{"message": "..."}` 로 내려가 화면에 표시된다.
메서드마다 try-catch 를 반복하지 않아도 된다.

## ⚠️ 알려진 한계

| 항목 | 내용 |
|---|---|
| 승인 권한 검사 없음 | `approve`·`reject` 가 **리더인지 확인하지 않는다.** crewId·userId 만 알면 누구나 승인할 수 있다 |
| `crew_events` 미완성 | 테이블과 엔티티는 있으나 등록 API 가 없다. `upcoming` 은 조회만 된다 |
| `attend` 미사용 | 참석 여부 컬럼이 있으나 변경 API 가 없다 |

첫 항목은 파티의 `delete`·`end` 처럼 `userId` 를 받아 리더와 비교하면 막을 수 있다.
[20_라이딩_매칭.md](20_라이딩_매칭.md) 의 `SecurityException` 방식이 참고가 된다.
