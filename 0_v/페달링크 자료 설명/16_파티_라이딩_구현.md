## 1. 파티 라이딩 진입 — 라우팅에 쿼리스트링 추가

### 문제

기존 라우팅은 `window.location.pathname` 만 봤다.

```jsx
const [currentPath, setCurrentPath] = useState(window.location.pathname);
if (currentPath === '/map') return <MapPage ... />;
```

여기에 `/map?partyId=3` 을 넣으면 `currentPath` 가 `'/map?partyId=3'` 이 되어
**모든 경로 비교가 어긋난다.** 어떤 페이지도 렌더되지 않는다.

### 해결 — path 와 search 를 분리해서 보관

```jsx
const [currentPath, setCurrentPath] = useState(window.location.pathname);
const [search, setSearch] = useState(window.location.search);

const moveTo = (path) => {
  window.history.pushState(null, '', path);
  const [onlyPath, query] = path.split('?');   // '/map?partyId=3' → '/map' + 'partyId=3'
  setCurrentPath(onlyPath);
  setSearch(query ? `?${query}` : '');
};

// 뒤로가기도 둘 다 갱신해야 한다
const handlePopState = () => {
  setCurrentPath(window.location.pathname);
  setSearch(window.location.search);
};
```

읽을 때는 브라우저 표준 `URLSearchParams` 를 쓴다.

```jsx
if (currentPath === '/map') {
  const partyId = new URLSearchParams(search).get('partyId');
  return <MapPage user={user} partyId={partyId} onBackHome={moveHome} />;
}
```

> React Router 를 쓰면 `useSearchParams` 로 해결되는 부분이다.
> 이 프로젝트는 라우터 없이 `history` API 로 직접 구현했으므로 직접 다뤄야 한다.

### 진입 버튼

파티 카드에서 **모집이 끝났고(`full`) 참여가 확정된 사람**에게 버튼이 보인다.

```jsx
const canRide = !ended && full && (isHost || myState === 'joined');
```

호스트도 파티 개설 시 `participants` 에 `joined` 로 자동 등록되므로 같은 조건에 묶인다.
문구만 역할에 따라 다르게 한다 — 호스트 "라이딩 시작", 참가자 "라이딩 합류".

## 2. 파티 멤버만 위치 표시

### 기존 동작의 문제

`GET /api/locations?userId=X` 는 **접속자 전원**을 돌려줬다.
모르는 사람에게 내 위치가 보이고, 지도에 무관한 마커가 섞인다.

### 백엔드 — 선택 파라미터로 좁히기

```java
@Transactional(readOnly = true)
@GetMapping("/locations")
public ResponseEntity<List<LiveLocation>> others(@RequestParam Long userId,
                                                 @RequestParam(required = false) Long partyId) {
    locations.values().removeIf(l -> now - l.updatedAt() > STALE_MS);

    Set<Long> allowed = (partyId == null) ? null : joinedMemberIds(partyId);

    return ResponseEntity.ok(locations.values().stream()
            .filter(l -> !l.userId().equals(userId))
            .filter(l -> allowed == null || allowed.contains(l.userId()))
            .toList());
}

/** 없는 파티면 빈 집합 → 아무도 안 보인다 (실패 시 더 많이 보여주지 않는다) */
private Set<Long> joinedMemberIds(Long partyId) {
    return partyRepository.findById(partyId)
            .map(Party::getMembers)
            .map(ms -> ms.stream().filter(m -> "joined".equals(m.getStatus()))
                    .map(m -> m.getUser().getId()).collect(Collectors.toSet()))
            .orElse(Set.of());
}
```

### 짚어둘 점 두 가지

**① `@Transactional(readOnly = true)` 가 필요하다**
`Party.members` 는 `FetchType.LAZY` 라 트랜잭션 밖에서 읽으면 `LazyInitializationException` 이 난다.
지금은 `spring.jpa.open-in-view` 기본값(true) 덕에 우연히 동작하지만,
그 설정을 끄는 순간 조용히 깨진다. 그래서 명시했다.

**② 실패할 때 "덜 보여주는" 쪽으로 기울인다**
없는 파티 id 가 오면 빈 집합을 돌려준다. 반대로 `null` 을 돌려 전체를 보여주면
잘못된 요청 하나로 위치가 새어나간다.

### 검증 결과

```
userId=2 시점 (파티 1 멤버 = testuser(2), sosos(3) / 외부인 ajkajk(4))
  partyId 없음  → ['참가자', '외부인']
  partyId=1    → ['참가자']            ← 멤버만
  없는 파티      → []                  ← 아무도 안 보임
```

## 3. 파티 코스 자동 표시

지도가 파티 모드로 열리면 파티에 걸린 코스를 그린다.

```jsx
useEffect(() => {
  if (!partyId) return;
  let alive = true;

  // 서로 보이지 않으면 파티 라이딩이 성립하지 않으므로 위치공유를 자동으로 켠다
  setLocationShareEnabled(true);
  localStorage.setItem('locationShareEnabled', 'true');
  if (user?.id) updateLocationSharing(user.id, true).catch(() => {});

  (async () => {
    const p = await getParty(partyId);
    if (!alive) return;
    setParty(p);

    if (p.routeId) {
      const route = await getRouteById(p.routeId);
      if (!alive || !mapRef.current) return;      // await 사이에 언마운트됐을 수 있다
      const bike = route.bikeRoute.map(pt => [pt.lat, pt.lng]);
      const shortest = route.shortestRoute.map(pt => [pt.lat, pt.lng]);
      drawRoutes(bike, shortest, routeLayerRef.current, mapRef.current);
    }
  })();

  return () => { alive = false; };
}, [partyId, user?.id]);
```

`await` 이 두 번 있으므로 `alive` 확인도 두 번 한다. 네트워크를 기다리는 사이
사용자가 페이지를 떠나면 사라진 지도에 그리려다 에러가 난다.

## 4. 팔로우 모드 + heading-up

### 용어

| 용어 | 뜻 |
|---|---|
| **follow mode / tracking** | 지도 중심이 내 위치를 계속 따라감 |
| **auto-recenter** | 위치 갱신마다 중앙으로 다시 맞춤 |
| **north-up** | 지도는 항상 북쪽이 위, 마커만 이동 |
| **heading-up / course-up** | 진행 방향이 항상 위로 오도록 회전 |

### 왜 마커만 회전시켰나

**Leaflet 코어에는 지도 회전 기능이 없다.** north-up 만 지원한다.
지도 자체를 돌리려면 `leaflet-rotate` 플러그인이 필요한데,
마지막 업데이트가 2023-07 로 2년 넘게 멈춰 있어 마커·팝업과 충돌 위험이 있다.

그래서 **지도는 북쪽 고정, 마커만 방위각만큼 회전**시켰다.
스트라바를 비롯한 대부분의 자전거 앱이 쓰는 방식이다.

```jsx
export function makeHeadingIcon(headingDeg) {
  return L.divIcon({
    html: `<div style="transform:rotate(${headingDeg}deg);transform-origin:50% 50%;">
      <svg viewBox="0 0 34 34" width="34" height="34">
        <circle cx="17" cy="17" r="15" fill="#2563eb" fill-opacity="0.18"/>
        <path d="M17 4 L25 26 L17 21 L9 26 Z" fill="#2563eb" stroke="#fff" stroke-width="1.6"/>
      </svg>
    </div>`,
    iconSize: [34, 34], iconAnchor: [17, 17],
  });
}
```

### 방향(heading)을 구하는 3가지 방법과 선택

| 방법 | 문제 |
|---|---|
| `coords.heading` | **정지 중이면 `null`**, 기기에 따라 아예 없음 |
| `DeviceOrientationEvent` (나침반) | iOS 13+ 는 별도 권한 요청 필요, HTTPS 필수 |
| 직전 좌표와의 방위각 | 움직여야만 나오지만 **가장 안정적** |

라이딩 중에는 계속 움직이므로 1순위 → 3순위 순으로 폴백한다.

```jsx
if (typeof pos.coords.heading === 'number' && !Number.isNaN(pos.coords.heading)) {
  headingRef.current = pos.coords.heading;
} else if (prev) {
  const moved = calculateDistance(prev.lat, prev.lng, latitude, longitude);
  if (moved > 3) {                                    // ★ 3m 필터
    headingRef.current = (bearingBetween(prev, cur) + 360) % 360;
  }
}
```

**3m 필터가 핵심이다.** GPS 는 제자리에서도 몇 미터씩 흔들려서,
필터가 없으면 신호등에 서 있는 동안 화살표가 팽이처럼 돈다.

### 방위각 공식

```js
export function bearingBetween(from, to) {
  const toRad = (d) => (d * Math.PI) / 180;
  const lat1 = toRad(from.lat), lat2 = toRad(to.lat);
  const dLng = toRad(to.lng - from.lng);
  const y = Math.sin(dLng) * Math.cos(lat2);
  const x = Math.cos(lat1) * Math.sin(lat2) - Math.sin(lat1) * Math.cos(lat2) * Math.cos(dLng);
  return (Math.atan2(y, x) * 180) / Math.PI;   // -180~180
}
```

서울시청 기준 검증: 북 0.0° / 동 90.0° / 남 180.0° / 서 270.0° / 북동 38.4° — 오차 3° 이내.

### `panTo` 를 쓰는 이유

```jsx
if (followingRef.current) {
  map.panTo([latitude, longitude], { animate: true, duration: 0.5 });
}
```

`setView` 는 **줌 레벨을 매번 고정**해서, 사용자가 확대·축소한 것을 1초마다 되돌려버린다.
`panTo` 는 중심만 옮긴다.

### state 가 아니라 ref 를 읽는 이유

```jsx
const followingRef = useRef(false);
useEffect(() => { followingRef.current = following; }, [following]);
```

`watchPosition` 콜백은 마운트 때 **한 번만** 만들어진다.
그 안에서 `following` state 를 직접 읽으면 클로저에 갇힌 **초기값 `false` 만 영원히** 본다.

### 팔로우 해제와 복귀

```jsx
// 사용자가 지도를 끌면 팔로우를 끈다.
// 없으면 다른 곳을 보려 옮겨도 다음 GPS 갱신에 내 위치로 튕겨 돌아온다.
map.on('dragstart', () => setFollowing(false));
```

**"내 위치로" 버튼은 오른쪽 아래**에 뒀다.

- 왼쪽 경로 패널(360px)과 겹치지 않음
- 오른쪽 위 줌 컨트롤과도 겹치지 않음
- 모바일에서 엄지가 닿는 자리 (카카오맵·네이버지도·구글맵 동일)

버튼이 팔로우 상태를 색으로 보여준다 — 켜짐이면 파란 배경, 꺼짐이면 흰 배경.

## 5. 라이딩 시작/종료 분리

기존에는 문구만 바뀌는 토글 버튼 하나였다. 이를 두 개로 나누고,
지금 누를 수 없는 쪽은 `disabled` 로 둔다.

```jsx
<div className="plannerRideAction">   {/* display:grid; gap:10px */}
  <button onClick={handleRideStart} disabled={isRiding}>라이딩 시작</button>
  <button onClick={handleRideStop} disabled={!isRiding}>라이딩 종료</button>
</div>
```

### 종료가 하는 일 5가지

```jsx
const handleRideStop = useCallback(async () => {
  setIsRiding(false);
  setFollowing(false);
  currentLocMarkerRef.current?.setIcon(makeCurrentLocationIcon());  // 화살표 → 파란 점

  // ① 타이머·GPS 감시 중지
  // ② 주행 기록 저장 (아래 7절)

  // ③ 위치 공유 해제 — 라이딩이 끝나면 계속 뿌릴 이유가 없다
  setLocationShareEnabled(false);
  localStorage.setItem('locationShareEnabled', 'false');
  if (user?.id) updateLocationSharing(user.id, false).catch(() => {});

  // ④ 파티 라이딩이고 내가 호스트면 파티도 종료
  if (party && user?.id === party.hostId) {
    const ended = await endParty(party.id, user.id);
    setParty(ended);
  }
}, [user?.id, rideTime, rideDistance, party]);
```

### 파티 종료는 호스트만

```java
@Transactional
public PartyResponse end(Long partyId, Long userId) {
    Party party = findParty(partyId);
    if (!party.getHost().getId().equals(userId)) {
        throw new SecurityException("호스트만 파티를 종료할 수 있습니다");
    }
    party.setStatus("ended");        // open | full | ended
    return toResponse(partyRepository.save(party));
}
```

참가자가 종료를 눌러도 **본인 라이딩만** 끝난다(기록 저장 + 위치공유 해제).
파티 상태는 호스트만 바꿀 수 있다.

`apply()` 가 이미 `if (!"open".equals(party.getStatus()))` 로 막고 있어,
`ended` 파티에는 신청이 자동으로 차단된다.

## 6. 참가자 자동 출발

### 왜 신호만 공유하는가

**서버는 남이 얼마나 달렸는지 알 수 없다.** 거리·시간은 각자 브라우저의 GPS 가 잰다.
그래서 "같이 출발"이라는 **신호만 맞추고**, 측정은 각자 한다.

### 백엔드 — 시작 시각 기록

```java
// Party 엔티티
private LocalDateTime rideStartedAt;   // 호스트가 출발한 시각

// PartyService — 호스트만
@Transactional
public PartyResponse startRide(Long partyId, Long userId) {
    Party party = findParty(partyId);
    if (!party.getHost().getId().equals(userId)) {
        throw new SecurityException("호스트만 라이딩을 시작할 수 있습니다");
    }
    party.setRideStartedAt(LocalDateTime.now());
    return toResponse(partyRepository.save(party));
}
```

### 프론트 — 호스트는 알리고, 참가자는 감지한다

```jsx
// 호스트: 시작하면 서버에 알림
if (party && user?.id === party.hostId && !party.rideStartedAt) {
  startPartyRide(party.id, user.id).then(setParty).catch(() => {});
}

// 참가자: 5초마다 파티를 확인하다가 rideStartedAt 이 생기면 자동 출발
useEffect(() => {
  if (!partyId || !party) return;
  const isHost = user?.id === party.hostId;
  if (isHost || isRiding || party.rideStartedAt) return;

  const timer = setInterval(async () => {
    const p = await getParty(partyId);
    if (p.rideStartedAt) {
      setParty(p);
      handleRideStart();
      showToast('호스트가 라이딩을 시작했습니다.');
    }
  }, 5000);
  return () => clearInterval(timer);
}, [partyId, party?.hostId, party?.rideStartedAt, isRiding, user?.id]);
```

### 한계

- **최대 5초 지연** — 폴링 주기. 즉시 맞추려면 WebSocket 이 필요하다
- **참가자가 지도에 있어야 한다** — 파티 페이지에만 있으면 폴링이 돌지 않는다

## 7. 파티별 주행 기록 — 저장 구조

### 검토한 4가지 방식

| 방식 | 내용 | 판단 |
|---|---|---|
| **A. 각자 측정 + `party_id`** | 멤버마다 자기 GPS 값으로 한 행 | ✅ 채택 |
| B. 호스트 기록 복사 | 한 번에 N 행, 값은 모두 동일 | 중간에 빠진 사람도 완주로 기록됨 → 거짓 |
| C. 서버가 위치 보고로 계산 | 3초 폴링 좌표를 누적 | 메모리라 재시작 시 소실, 상태 관리 복잡 |
| D. `party_rides` 테이블 분리 | 주행 회차를 별도 관리 | 정석이지만 지금 규모엔 과함 |

### 채택한 구조

```sql
ALTER TABLE ride_records ADD COLUMN party_id BIGINT;   -- 혼자 탄 기록이면 NULL
```

실제 저장 결과:

```
id | user_id | 이름              | party_id | distance_km | duration_min
 1 |    2    | testuser         |   NULL   |    4.21     |     34     ← 혼자
 2 |   14    | test             |    3     |   15.2      |     52     ← 파티, 호스트
 3 |   13    | qwerwer@...      |    3     |   14.8      |     55     ← 파티, 참가자
```

**거리가 서로 다른 것이 정상이다.** 각자 실제로 지나온 경로가 다르기 때문이고,
그게 사실이다. 호스트 값을 복사했다면 누적 거리가 실제와 어긋나기 시작한다.

파티 단위 집계도 자연스럽게 된다.

```sql
SELECT party_id, count(*), sum(distance_km), avg(distance_km)
FROM ride_records WHERE party_id IS NOT NULL GROUP BY party_id;
-- 3 | 2 | 30.0 | 15.0
```

프론트는 저장할 때 파티 id 를 함께 보낸다.

```jsx
await api.post('/api/ride-records', {
  userId: user.id,
  distance: rideDistance / 1000,
  duration,
  partyId: party ? party.id : null,
});
```

## 8. 파티 삭제

### 백엔드 — 호스트만

```java
@Transactional
public void delete(Long partyId, Long userId) {
    Party party = findParty(partyId);
    if (!party.getHost().getId().equals(userId)) {
        throw new SecurityException("호스트만 삭제할 수 있습니다");
    }
    partyRepository.delete(party);
}
```

```java
@DeleteMapping("/{id}")
public ResponseEntity<?> delete(@PathVariable Long id, @RequestParam Long userId) { ... }
```

> 이 프로젝트에서 **HTTP DELETE 를 실제로 쓰는 첫 엔드포인트**다.
> 경로 삭제(`POST /api/routes/delete`)는 id 배열을 body 로 보내려고 POST 를 썼다.

### 무엇이 같이 지워지고 무엇이 남는가

```java
// Party 엔티티
@OneToMany(mappedBy = "party", cascade = CascadeType.ALL, orphanRemoval = true)
private List<PartyMember> members;
```

| 대상 | 결과 | 이유 |
|---|---|---|
| `party_members` | **함께 삭제** | `cascade = ALL` — 파티가 없으면 참가 기록도 의미가 없다 |
| `ride_records.party_id` | **남음** | 외래키가 아니다. 실제로 달린 사실은 파티를 지운다고 사라지지 않는다 |

실제 검증:

```
              삭제 전 → 삭제 후
parties          8   →   7
party_members   17   →  15     ← 참가자 2명 함께 삭제
ride_records     2   →   2     ← 주행 기록 유지
```

### 확인 단계

이 프로젝트는 커밋 `66ec63b` 에서 **OS 기본 `confirm()` 을 전부 제거**했다.
그래서 카드 안에서 확인받는다.

```jsx
const [confirmingDelete, setConfirmingDelete] = useState(false);

{confirmingDelete && (
  <div className="partyDeleteConfirm">
    <p>이 링크를 삭제할까요? 참가 신청도 함께 사라집니다.</p>
    <button onClick={() => setConfirmingDelete(false)}>취소</button>
    <button className="partyDeleteYesBtn" onClick={() => onDelete(party.id)}>삭제</button>
  </div>
)}
```

## 9. 경로 목록 접근 제한 (버그 수정)

### 발견한 문제

파티 페이지의 "내 저장 경로" 목록이 **비로그인 상태에서 남의 경로를 전부 보여줬다.**

```js
getRoutes(undefined)  →  GET /api/routes  (userId 없음)  →  백엔드가 전체 반환
```

지도의 "저장된 경로 목록" 버튼도 같은 문제였다.

### 백엔드 — `userId` 를 필수로

```java
@GetMapping("/routes")
public ResponseEntity<?> getRouteList(@RequestParam(required = false) Long userId) {
    if (userId == null) {
        return ResponseEntity.badRequest().body(Map.of("message", "userId는 필수입니다"));
    }
    return ResponseEntity.ok(routeService.getRouteList(userId));
}
```

프론트를 우회해 API 를 직접 호출해도 남의 경로가 나가지 않는다.

> 둘러보기 피드(`FeedService`)는 리포지토리를 직접 쓰므로 이 변경의 영향을 받지 않는다.
> 바꾸기 전에 호출처를 전부 확인했다.

### 프론트 — 비로그인이면 호출조차 하지 않음

```js
export async function getMyRoutesForParty(userId) {
    if (!userId) return [];   // 백엔드가 400 을 주므로 아예 부르지 않는다
    ...
}
```

파티 페이지는 그 자리에 안내와 로그인 버튼을 띄우고,
지도는 "로그인 후 이용할 수 있습니다" 토스트를 보여준다.

## 10. 파티 예외를 400 으로 (버그 수정)

### 문제

`PartyService` 는 사용자 실수에도 `RuntimeException` 을 던졌고,
Spring 이 이를 **메시지 없는 500** 으로 내보냈다.

```json
{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/api/parties/4/apply"}
```

프론트가 "왜 안 되는지" 표시할 수 없다.

### 해결 — 파티 액션에 한정해 변환

```java
private ResponseEntity<?> handle(Supplier<PartyResponse> action) {
    try {
        return ResponseEntity.ok(action.get());
    } catch (RuntimeException e) {
        return ResponseEntity.badRequest().body(Map.of("message", e.getMessage()));
    }
}
```

**전역 `@RestControllerAdvice` 를 쓰지 않은 이유**: 모든 `RuntimeException` 을 400 으로 바꾸면
NullPointerException 같은 **진짜 버그까지 "정상적인 사용자 오류"로 위장**된다.
그러면 로그에도 안 남고 원인을 찾기 어려워진다.

결과:

```
종료된 파티에 신청  → 400 {"message":"신청할 수 없는 파티입니다."}
중복 신청          → 400 {"message":"이미 신청했습니다."}
```

## 외부 공개 (cloudflared 터널)

시연을 위해 로컬 서버를 인터넷 HTTPS 주소로 여는 방법.

```bash
# 1. 백엔드 터널
cloudflared tunnel --url http://localhost:8080/
#    → https://xxx.trycloudflare.com 발급

# 2. .env.local 에 백엔드 터널 주소 지정
VITE_API_BASE=https://xxx.trycloudflare.com

# 3. Vite 재시작 (환경변수는 시작할 때만 읽는다)

# 4. 프론트 터널 → 이 주소를 공유
cloudflared tunnel --url http://localhost:3000/
```

### CRA 시절과 달라진 점 2가지

**① 환경변수 이름**
`REACT_APP_API_BASE` → **`VITE_API_BASE`**.
Vite 는 `REACT_APP_` 접두사를 무시하므로, 옛 이름을 쓰면 조용히
`http://localhost:8080` 으로 폴백해 **상대방 브라우저에서 API 가 전부 실패**한다.

**② 호스트 차단 해제**
`DANGEROUSLY_DISABLE_HOST_CHECK` 는 CRA 전용이다. Vite 는 이렇게 한다.

```js
// vite.config.mjs
server: {
  allowedHosts: ['.trycloudflare.com'],   // 도메인을 한정해 CRA 방식보다 안전
}
```

백엔드 CORS 는 `WebConfig` 에 이미 `https://*.trycloudflare.com` 이 열려 있다.

### 공개 전 알아둘 위험

이 앱은 **인증이 없다.** `userId` 를 클라이언트가 보내면 서버가 그대로 믿는다.
특히 경로 삭제 API 는 권한 검사가 아예 없어서,
**URL 을 아는 사람이면 누구나 모든 사용자의 저장 경로를 지울 수 있다.**

팀 시연 정도면 괜찮지만 링크가 퍼지지 않게 하고, 끝나면 터널을 닫아야 한다.
