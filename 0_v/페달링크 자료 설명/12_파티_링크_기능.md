# 파티(링크) 기능 — 모집 · 신청 · 승인

> 저장한 경로를 걸어서 "같이 탈 사람"을 모으는 기능. UI에서는 파티를 **"링크"** 라고 부른다.
> 커밋 `4adb372`(백엔드 구현 + 프론트 mock 제거), `66ec63b`(로그인 체크 추가)로 완성됐다.
> 이 프로젝트에서 **JPA 연관관계와 상태 관리를 제대로 쓰는 유일한 기능**이라 공부하기 좋다.

## 사용자 눈으로 본 흐름

```
호스트                                   참가자
  │                                        │
  ├─ 지도에서 경로 저장                       │
  ├─ /party 에서 그 경로로 "링크 만들기"        │
  │   (제목, 모임시간, 최대인원)                │
  │        └──▶ 파티 생성 (status: open)      │
  │             호스트는 자동으로 joined        │
  │                                        │
  │                              ◀─ 목록에서 "참여 신청" (pending)
  │                                        │
  ├─ "승인 대기" 목록에서 수락/거절             │
  │        └──▶ joined / rejected           │
  │                                        │
  └─ 정원이 차면 status: full → 신청 버튼 "모집 완료"로 잠김
```

## 1. 데이터 모델 — 왜 테이블을 2개로 나눴나

"파티에 누가 참여했는가"를 파티 테이블 안에 넣을 수는 없다. 한 파티에 사람이 여럿이고,
한 사람이 여러 파티에 들어갈 수 있는 **다대다(N:M)** 관계이기 때문이다.

관계형 DB에서 다대다는 **중간 테이블**로 푼다.

```
users ──1:N──▶ party_members ◀──N:1── parties
                    │
                    └─ status: pending | joined | rejected
```

중간 테이블(`party_members`)에 **상태 컬럼을 같이 두는 것**이 포인트다.
"신청함 / 확정됨 / 거절됨"이 전부 같은 행의 상태 변화로 표현된다.
테이블을 세 개(신청 / 참가자 / 거절)로 나눴다면 데이터를 옮겨다녀야 해서 훨씬 복잡해진다.

```java
// PartyMember.java
@Entity
@Table(name = "party_members", uniqueConstraints = {
        @UniqueConstraint(columnNames = {"party_id", "user_id"})   // 중복 신청 차단
})
@Data
public class PartyMember {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "party_id", nullable = false)
    private Party party;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id", nullable = false)
    private User user;

    @Column(nullable = false, length = 20)
    private String status = "pending";     // pending | joined | rejected

    private LocalDateTime joinedAt = LocalDateTime.now();
}
```

```java
// Party.java (핵심 부분)
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "host_user_id", nullable = false)
private User host;

private Long routeId;                      // ★ Route 엔티티가 아니라 id만 들고 있다

@OneToMany(mappedBy = "party", cascade = CascadeType.ALL, orphanRemoval = true)
private List<PartyMember> members = new ArrayList<>();

private String status = "open";            // open | full
private int maxMembers = 6;
```

> 📌 `routeId` 를 `@ManyToOne Route route` 로 안 하고 **`Long` 으로 둔 이유**:
> 경로가 삭제돼도 파티는 남아야 하고, 파티 조회 때마다 무거운 좌표(LineString)까지
> 딸려오는 걸 피하려는 것. 대신 경로 정보가 필요하면 서비스에서 따로 조회한다.
> (단점: DB 외래키 제약이 없어서 없는 경로 id를 넣어도 막히지 않는다)

### 상태값을 String으로 둔 것에 대해

`"open"`, `"pending"` 같은 문자열은 오타를 컴파일러가 못 잡는다.
자바 `enum` + `@Enumerated(EnumType.STRING)` 으로 바꾸면 오타가 컴파일 에러가 되어 안전해진다.
지금은 문자열이므로 **비교할 때 항상 `"joined".equals(m.getStatus())` 순서**로 써서
`null` 이어도 터지지 않게 하고 있다.

## 2. 백엔드 로직 — PartyService

### 개설 — 호스트를 자동으로 참가자에 넣는다

```java
@Transactional
public PartyResponse createParty(PartyRequest req) {
    User host = findUser(req.getHostId());

    Party party = new Party();
    party.setHost(host);
    party.setRouteId(req.getRouteId());
    party.setTitle(req.getTitle());
    party.setStartAt(req.getStartAt());
    party.setMaxMembers(req.getMaxMembers());
    Party saved = partyRepository.save(party);

    // 호스트는 자동으로 joined 상태로 참여
    PartyMember hostMember = new PartyMember();
    hostMember.setParty(saved);
    hostMember.setUser(host);
    hostMember.setStatus("joined");
    partyMemberRepository.save(hostMember);

    return toResponse(partyRepository.findById(saved.getId()).get());
}
```

호스트도 `party_members` 에 넣기 때문에 **"현재 인원"을 셀 때 예외 처리가 필요 없다.**
호스트를 따로 뒀다면 인원 계산마다 `+1` 을 해야 하고 어딘가에서 빼먹게 된다.

`@Transactional` 이 있어서 파티 저장과 호스트 멤버 저장이 **한 덩어리**로 처리된다.

### 신청 — 두 가지 검사

```java
@Transactional
public PartyResponse apply(Long partyId, Long userId) {
    Party party = findParty(partyId);
    User user = findUser(userId);

    if (partyMemberRepository.existsByPartyAndUser(party, user))
        throw new RuntimeException("이미 신청했습니다.");
    if (!"open".equals(party.getStatus()))
        throw new RuntimeException("신청할 수 없는 파티입니다.");

    PartyMember member = new PartyMember();
    member.setParty(party); member.setUser(user); member.setStatus("pending");
    partyMemberRepository.save(member);

    return toResponse(partyRepository.findById(partyId).get());
}
```

### 승인 — 정원 검사 + 자동 마감

```java
@Transactional
public PartyResponse approve(Long partyId, Long userId) {
    Party party = findParty(partyId);
    PartyMember member = partyMemberRepository.findByPartyAndUser(party, findUser(userId))
            .orElseThrow(() -> new RuntimeException("신청 내역 없음"));

    long joinedCount = party.getMembers().stream()
            .filter(m -> "joined".equals(m.getStatus())).count();

    if (joinedCount >= party.getMaxMembers())
        throw new RuntimeException("정원이 초과되었습니다.");

    member.setStatus("joined");
    partyMemberRepository.save(member);

    if (joinedCount + 1 >= party.getMaxMembers()) {   // 이번 승인으로 정원이 찼다면
        party.setStatus("full");
        partyRepository.save(party);
    }
    return toResponse(partyRepository.findById(partyId).get());
}
```

**세 메서드 모두 마지막에 "갱신된 파티 전체"를 반환한다.**
프론트는 응답으로 받은 객체 하나만 목록에서 갈아끼우면 되므로, 목록을 다시 부를 필요가 없다.

### 알려진 문제 3가지

| 문제 | 설명 |
|------|------|
| 예외가 500으로 나간다 | `RuntimeException` 은 Spring이 500으로 변환한다. "이미 신청했습니다"는 사용자 실수이므로 **400**이 맞다 → `@RestControllerAdvice` 로 변환 필요 |
| 권한 검사가 없다 | `approve`/`reject` 를 **호스트가 아닌 사람도 호출할 수 있다.** `party.getHost().getId()` 와 요청자를 비교해야 하는데, 애초에 요청자를 알 방법(인증)이 없다 |
| 취소 기능이 없다 | 파티 삭제, 참가 취소, 거절된 사람의 재신청 API가 없다 |

## 3. 응답 DTO — PartyResponse

엔티티를 그대로 JSON으로 내보내면 `Party → members → party → members …` 무한 순환이 나고,
`User` 의 비밀번호 해시까지 노출된다. 그래서 화면에 필요한 형태로 새로 만든다.

```java
public static PartyResponse from(Party party) {
    PartyResponse r = new PartyResponse();
    r.id = party.getId();
    r.title = party.getTitle();
    r.hostId = party.getHost().getId();
    r.hostName = party.getHost().getName();
    r.status = party.getStatus();
    r.maxMembers = party.getMaxMembers();

    // ★ 멤버를 상태별로 갈라서 담는다 — 프론트가 필터링할 필요 없음
    r.participants = party.getMembers().stream()
            .filter(m -> "joined".equals(m.getStatus()))
            .map(PartyResponse::toDto).collect(Collectors.toList());

    r.pendingRequests = party.getMembers().stream()
            .filter(m -> "pending".equals(m.getStatus()))
            .map(PartyResponse::toDto).collect(Collectors.toList());
    return r;
}
```

경로 정보는 서비스에서 따로 채운다.

```java
private PartyResponse toResponse(Party party) {
    PartyResponse r = PartyResponse.from(party);
    if (party.getRouteId() != null) {
        routeRepository.findById(party.getRouteId()).ifPresent(route -> {
            r.setRouteName(route.getRouteName());
            r.setFromLabel(route.getFromLabel());
            r.setToLabel(route.getToLabel());
        });
    }
    return r;
}
```

> ✅ `distanceKm` 은 이제 `routes.distance_km` 에서 채워진다.
> 경로를 저장할 때 BRouter 분석값(`routeStats.distanceKm`)을 함께 보내 컬럼에 넣어두고,
> `toResponse()` 가 그 값을 파티 응답에 실어준다.
> **단, 이 기능이 생기기 전에 저장된 경로는 `null`** 이라 거리 표시가 안 나온다.

> ⚠️ **N+1 문제**: `getParties()` 는 파티 목록을 가져온 뒤 **파티마다** 호스트 조회 + 경로 조회를
> 따로 실행한다. 파티가 20개면 쿼리가 40번 넘게 나간다. 지금 규모에서는 문제없지만,
> 개선하려면 `@EntityGraph` 나 fetch join 을 쓴다.

## 4. 프론트 — PartyPage.js

### 화면 구성

```
┌─────────────────────────────────┐
│  히어로 (배경 이미지 + 문구)         │
├─────────────────────────────────┤
│ ① 내 저장 경로로 링크 만들기          │  ← 경로마다 카드 + 접히는 개설 폼
│   [경로 A] [링크 만들기]             │
│   [경로 B] [링크 만들기]             │
├─────────────────────────────────┤
│ ② 모집 중인 링크                    │  ← 파티 카드 그리드
│   [파티1] [파티2] [파티3]            │
└─────────────────────────────────┘
```

### 데이터 로드

```js
useEffect(() => {
  let alive = true;
  Promise.all([getMyRoutesForParty(user?.id), getParties()]).then(([r, p]) => {
    if (!alive) return;                 // 언마운트 후 setState 방지
    setRoutes(r); setParties(p); setLoading(false);
  });
  return () => { alive = false; };
}, []);
```

### 목록에서 해당 파티만 교체

```js
const replaceParty = (updated) =>
  setParties(prev => prev.map(p => (p.id === updated.id ? updated : p)));

const handleApply   = async (id)             => replaceParty(await applyToParty(id, me));
const handleApprove = async (partyId, userId) => replaceParty(await approveRequest(partyId, userId));
const handleReject  = async (partyId, userId) => replaceParty(await rejectRequest(partyId, userId));
```

**서버 응답으로 통째로 갈아끼우는 방식**의 장점: 프론트가 "승인하면 participants에 넣고
pendingRequests에서 빼고 정원 차면 full로 바꾸고…" 같은 로직을 **중복으로 구현할 필요가 없다.**
서버가 계산한 결과를 그대로 믿는다.

### 버튼 상태를 데이터에서 유도하기

```js
const isHost = party.hostId === me.id;
const full   = party.participants.length >= party.maxMembers;
const myState = party.participants.some(m => m.userId === me.id)   ? 'joined'
              : party.pendingRequests.some(m => m.userId === me.id) ? 'pending'
              : 'none';
```

```js
if (!isLoggedIn)          return <button onClick={onLoginNeeded}>로그인 후 신청</button>;
if (myState === 'joined') return <button disabled>✓ 참여 확정</button>;
if (myState === 'pending')return <button disabled>승인 대기중</button>;
if (full)                 return <button disabled>모집 완료</button>;
return <button onClick={onApply}>참여 신청</button>;
```

버튼 상태를 별도 state로 들고 있지 않고 **파티 데이터에서 매번 계산**한다.
상태를 두 곳에 저장하면 반드시 어긋나기 때문에, "하나의 진실(서버 데이터)"에서 유도하는 게 안전하다.

### 비로그인 처리

로그인하지 않은 사용자에게는 `alert` 를 띄우지 않고 **버튼 문구 자체를 "로그인 후 신청"으로 바꾸고**
누르면 로그인 페이지로 보낸다 (`onMoveLogin`). 커밋 `66ec63b` 에서 정리된 부분이다.
