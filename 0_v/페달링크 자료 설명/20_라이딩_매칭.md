# 라이딩 매칭 — 즉석 동행 연결

## 이 프로젝트에서 쓰인 곳
- 파티 도크의 "근처 라이더" — 주변 사람에게 동행 신청
- 신청 수락 시 **파티가 자동으로 생성**된다
- 5분이 지난 신청은 자동 만료

관련 코드
- 백엔드 `controller/MatchController.java`, `service/MatchService.java`, `entity/MatchRequest.java`
- 프론트 `api/matches.js`, `components/PartyDock.jsx`

---

## 무엇을 해결하는 기능인가

기존 파티는 **경로를 먼저 만들고 사람을 모으는** 방식이다. 준비가 필요하다.

```
[파티]  경로 저장 → 파티 개설 → 시간 지정 → 모집 → 승인 → 라이딩
```

매칭은 그 반대다. **지금 근처에 있는 사람에게 바로 신청**한다.

```
[매칭]  근처 라이더 발견 → 신청 → 수락 → 파티 자동 생성 → 바로 라이딩
```

즉석에서 같이 탈 사람을 찾는 용도라 **수명이 5분으로 짧다.**

## MatchRequest 엔티티

```java
@ManyToOne @JoinColumn(name = "from_user_id", nullable = false)
private User fromUser;          // 신청한 사람

@ManyToOne @JoinColumn(name = "to_user_id", nullable = false)
private User toUser;            // 신청받은 사람

@Column(nullable = false, length = 20)
private String status = "pending";   // pending | accepted | rejected | expired

private Long partyId;           // 수락 시 만들어진 파티

@Column(nullable = false)
private LocalDateTime createdAt = LocalDateTime.now();
```

`partyId` 는 수락되기 전까지 `null` 이다. 수락 순간 생성된 파티의 id 가 채워진다.

## 신청 — 막아야 할 것들

`service/MatchService.java`

```java
@Transactional
public MatchRequest send(Long fromUserId, Long toUserId) {
    if (fromUserId.equals(toUserId)) {
        throw new RuntimeException("자기 자신에게는 신청할 수 없습니다.");
    }
    expireOld();

    if (partyService.isInActiveParty(fromUserId)) {
        throw new RuntimeException("이미 파티에 속해 있어서 신청할 수 없어요.");
    }
    if (partyService.isInActiveParty(toUserId)) {
        throw new RuntimeException("상대가 이미 다른 파티에 속해 있어요.");
    }
    matchRequestRepository
        .findByFromUser_IdAndToUser_IdAndStatus(fromUserId, toUserId, "pending")
        .ifPresent(r -> { throw new RuntimeException("이미 신청했어요. 상대의 응답을 기다려주세요."); });
    ...
}
```

| 검사 | 이유 |
|---|---|
| 자기 자신 | 파티가 1인으로 만들어지는 것을 막는다 |
| **양쪽 모두** 파티 소속 확인 | 이미 다른 사람과 타는 중이면 성사돼도 의미가 없다 |
| 중복 신청 | 같은 사람에게 여러 번 보내는 것을 막는다 |

**신청자뿐 아니라 상대도 검사한다**는 점이 핵심이다. 한쪽만 보면
"수락했더니 상대가 이미 다른 파티에 있음" 상태가 만들어진다.

## 수락 — 파티가 만들어지는 지점

```java
@Transactional
public PartyResponse accept(Long requestId, Long userId) {
    MatchRequest req = findRequest(requestId);

    if (!req.getToUser().getId().equals(userId)) {
        throw new SecurityException("본인에게 온 신청만 수락할 수 있어요.");
    }
    if (isExpired(req)) {
        req.setStatus("expired");
        matchRequestRepository.save(req);
        throw new RuntimeException("신청이 만료됐어요.");
    }
    if (!"pending".equals(req.getStatus())) {
        throw new RuntimeException("이미 처리된 신청이에요.");
    }

    PartyResponse party = partyService.createMatchedParty(
            req.getFromUser().getId(), req.getToUser().getId());
    req.setStatus("accepted");
    req.setPartyId(party.getId());
    matchRequestRepository.save(req);
    return party;
}
```

**세 검사의 순서에 의미가 있다.**

1. **권한** — 남의 신청을 대신 수락하는 것을 막는다
2. **만료** — 5분이 지났으면 그 자리에서 `expired` 로 바꾼다
3. **중복 처리** — 이미 수락·거절된 것을 다시 처리하지 않는다

`SecurityException` 만 따로 던지는 이유는 컨트롤러에서 **403** 으로 내리기 위해서다.

```java
} catch (SecurityException e) {
    return ResponseEntity.status(403).body(Map.of("message", e.getMessage()));
} catch (RuntimeException e) {
    return ResponseEntity.badRequest().body(Map.of("message", e.getMessage()));
}
```

권한 문제(403)와 상태 문제(400)는 클라이언트가 다르게 대응해야 하므로 구분한다.

> 참고 — 파티의 `approve`·`reject` 에는 이런 권한 검사가 **없다.** 매칭 쪽이 더 엄격하다.

## 5분 만료 — 스케줄러 없이

```java
private static final long EXPIRE_MINUTES = 5;

// 5분 지난 pending 신청을 만료 처리 — 별도 스케줄러 없이 조회/신청 시점마다 훑는다
private void expireOld() {
    LocalDateTime cutoff = LocalDateTime.now().minusMinutes(EXPIRE_MINUTES);
    List<MatchRequest> stale =
        matchRequestRepository.findByStatusAndCreatedAtBefore("pending", cutoff);
    if (stale.isEmpty()) return;
    stale.forEach(r -> r.setStatus("expired"));
    matchRequestRepository.saveAll(stale);
}
```

`@Scheduled` 배치를 두지 않고 **`send`·`listIncoming`·`listOutgoing` 이 불릴 때마다** 훑는다.

| | 배치 방식 | 현재 방식 |
|---|---|---|
| 정확도 | 주기마다 정확히 만료 | 누가 API 를 불러야 만료 |
| 복잡도 | 스케줄러 설정 필요 | 없음 |
| 빈 서비스일 때 | 계속 돌아감 | 아무 일도 안 함 |

프론트가 3초마다 폴링하므로 실제로는 거의 즉시 만료된다.
**아무도 접속하지 않으면 만료도 멈추지만**, 그때는 만료할 이유도 없다.

## outgoing 이 accepted 까지 주는 이유

```java
/**
 * 내가 보낸 신청 — pending(버튼 "신청 중" 표시용) + accepted(수락되면 프론트가 이걸 보고
 * 신청한 사람도 자동으로 파티 라이딩으로 전환한다. 수락자만 서버에서 알 수 있는 게 아니라
 * 신청자 쪽도 폴링으로 알아채야 하기 때문에 accepted 도 같이 내려준다).
 */
public List<MatchRequest> listOutgoing(Long userId) {
    expireOld();
    return matchRequestRepository
        .findByFromUser_IdAndStatusInOrderByCreatedAtDesc(userId, List.of("pending", "accepted"));
}
```

**수락은 받은 쪽에서 일어난다.** 서버는 신청자에게 먼저 알려줄 수단이 없다(채팅과 달리 WebSocket 을 안 쓴다).

```
B 가 수락 → B 화면은 즉시 파티로 전환
           A 는 어떻게 아는가?
              ↓
       A 가 /outgoing 을 폴링하다가 accepted 를 발견 → 자기도 전환
```

`pending` 만 내려주면 A 의 화면은 영영 "신청 중" 에 머문다.

## API

| 메서드 | 경로 | 기능 |
|---|---|---|
| POST | `/api/matches` | 신청 |
| GET | `/api/matches/incoming?userId=` | 받은 신청 (pending) |
| GET | `/api/matches/outgoing?userId=` | 보낸 신청 (pending + accepted) |
| POST | `/api/matches/{id}/accept` | 수락 → 파티 생성 |
| POST | `/api/matches/{id}/reject` | 거절 |

## 위치 기능과의 관계

"근처 라이더" 목록은 **실시간 위치 공유**에서 온다.

```
GET /api/locations?userId=&partyId=   ← 15초 내 위치를 보고한 사람들
                 ↓
        파티 도크가 목록으로 표시
                 ↓
        신청 버튼 → POST /api/matches
```

위치를 공유하지 않으면 남에게 보이지 않으므로 신청도 받을 수 없다.
